| sm | 8px | Gap between inputs and between Buy and Sell (`gap-2`), cell horizontal padding (`px-2`), input horizontal padding (`px-2`) |
| md | 16px | Form block horizontal padding (`px-4`), gap between the input group and the button group (`gap-4`), button horizontal padding (`px-4`) |
| lg | 24px | Empty/error state padding (`p-6`), reserved message line height (`h-6`) |
| xl | 32px | Control height: inputs, buttons, remove button (`h-8`, `size-8`) |
| 2xl | 48px | Form controls row height (`h-12`), same as the header |
| 3xl | 64px | Not used |

Exceptions (all multiples of 4, fixed component dimensions, not spacing tokens):
- Trade bar block and watchlist add block are each exactly 72px tall (`h-18`): a 48px controls row (`h-12`) plus a 24px reserved message line (`h-6`). The message line is always reserved, so showing or clearing a message never shifts layout.
- Trade bar control widths: ticker input 128px (`w-32`), quantity input 128px (`w-32`), Buy 80px (`w-20`), Sell 80px (`w-20`). Total 448px plus `px-4` padding = 480px, which fits the 544px workspace at the 1024px breakpoint.

- Watchlist table gains a fifth column, remove, 40px (`w-10`); the remove button is 32px (`size-8`) centered in the 40px row. The sparkline column shrinks from 168px to 128px at the 480px panel width. Existing widths (ticker 96, price 96, change 88) are unchanged.
- Positions title bar 40px (`h-10`), column-label row 32px (`h-8`), data rows 40px (`h-10`) (same as watchlist). Positions table minimum width 576px (`min-w-144`); ticker column 96px (`w-24`), the other five columns share the remaining width equally.
- No 12px, 20px or other off-scale spacing; no arbitrary `[..px]` spacing.

No new tokens. 60/30/10 holds: `surface` stays dominant, `panel` is the secondary surface for the trade bar, positions panel and watchlist panel, accent stays at its reserved uses.

| Role | Value | Usage in this phase |
|------|-------|---------------------|

| Secondary (30%) | `#161b22` (`panel`) | Trade bar, positions panel, watchlist panel. Row hover `#1c2128` (`raised`). Borders `#30363d` (`border`) on panel edges, input borders, row dividers |
| Accent (10%) | `#ecad0a` (`accent`) | See reserved list below (unchanged from Phase 2 plus focus rings on the new controls) |
| Destructive | `#f85149` (`down`) | Error message text, remove-button hover text. No destructive action has a confirmation step (see Copywriting Contract) |

Status and text colors used here:

| Token | Value | Usage in this phase |
|-------|-------|---------------------|
| `fg` | `#e6edf3` | Input text, success message, button label text, positions cells, P&L of exactly zero |
| `muted` | `#8b949e` | Placeholders, positions column labels, in-flight message ("Placing order..."), remove-button resting glyph, "--" |
| `up` / `down` | `#3fb950` / `#f85149` | P&L and P&L % sign coloring in the positions table via `toneClass`, exactly as the watchlist Chg % column. Never used for Buy/Sell buttons or for the success message |
| `secondary` | `#753991` | Fill of the Buy, Sell and Add buttons (the "submit button" reservation from Phase 2 is now consumed). Label `fg` on `secondary` computes to about 6.5:1 (WCAG luminance: `fg` 0.838, `secondary` 0.0875), passing AA |

Accent reserved for: (1) the "FinAlly" wordmark in the header, (2) the `:focus-visible` outline (2px, offset 2px) on every interactive control: Retry buttons, footer link, trade and watchlist inputs, Buy / Sell / Add buttons, and the per-row remove buttons. Nothing else. Accent is never used for prices, P&L, status, messages, rows or hover.

Rules:
- Buy and Sell are visually identical (solid `secondary`, label only differs). Green and red keep one meaning in this app (price direction and P&L), so they are never applied to the order buttons. Only the label and the position separate them (Buy first, Sell second, `gap-2` apart).
- Button states: hover `hover:brightness-110`; disabled `disabled:opacity-50 disabled:cursor-not-allowed` (disabled elements are exempt from contrast minimums); focus uses the accent outline.
- Inputs: `h-8 rounded-sm border border-border bg-surface px-2 text-body text-fg placeholder:text-muted`; `focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-accent`. The ticker input also has `uppercase` (CSS only, so the user sees what the server will store). The border never changes color on focus or error.
- Message line colors: pending `muted`, success `fg`, error `down`. Direction and meaning are never by color alone: every message is a full sentence, and errors carry `role`-level semantics through `aria-live` (below).
- Disconnected state (status `disconnected`): positions price, P&L and P&L % cells render at `opacity-60`, like the watchlist price/change cells and header numbers (Phase 2 decision 5). Quantity and avg cost do not depend on the stream and do not dim. Trade and watchlist forms are NOT disabled when disconnected (they use REST, and the server prices from its own cache).

### Trade bar (`<form aria-label="Trade" data-testid="trade-bar">`)

- Row 1 (48px, `px-4`, flex, items centered): ticker input (128px), `gap-2`, quantity input (128px), `gap-4`, Buy button (80px), `gap-2`, Sell button (80px). Inputs and buttons are 32px tall.
- Row 2 (24px, `px-4`): the message line (`FormMessage`), always present.
- Ticker input: `type="text"`, `placeholder="Ticker"`, `aria-label="Ticker"`, `autoComplete="off"`, `spellCheck={false}`, `autoCapitalize="characters"`, `uppercase`. No `maxLength` (a truncated paste would silently turn an invalid input into a different valid ticker; the server rejects bad shapes with `Invalid ticker: ...`).
- Quantity input: `type="text"`, `inputMode="decimal"`, `placeholder="Quantity"`, `aria-label="Quantity"`, `autoComplete="off"`, right-aligned, `tabular-nums`. NOT `type="number"` (it accepts `1e3`, shows spinners, and localizes the decimal separator).
- Buy and Sell are `type="button"`. The `<form>` has `onSubmit={(e) => e.preventDefault()}`. Pressing Enter in either input does nothing at all (no request, no message): market orders fill instantly with no confirmation dialog (PLAN.md), so an implicit submit is too easy to fire by accident. Tab order: ticker, quantity, Buy, Sell.
- Client-side validation runs before any request (exact copy in the Copywriting Contract). The quantity must match `^(\d+(\.\d{1,6})?|\.\d{1,6})$` and be greater than 0 after parsing. `1e3`, `10,5`, `-1`, `+1`, spaces inside the number, and empty are rejected. The ticker is trimmed and must be non-empty; its shape is otherwise the server's call.
- Submit sequence: validate, then set pending (both buttons `disabled`, message "Placing order...", `aria-busy="true"` on the form), then send, then apply `response.portfolio` to the portfolio store (success) or show the server `error` text (failure). When the request settles, focus moves to the quantity input.
- After success: ticker input keeps its value, quantity input is cleared, message shows the success sentence. After any failure: both inputs keep their values.
- The message clears (becomes empty) on any edit of either input and when the next submit starts. There is no timer-based auto-dismiss.

### Watchlist add block (inside `WatchlistPanel`, between the 40px title bar and the table)

- `<form aria-label="Add ticker to watchlist">`, 72px: controls row 48px (`px-4`, `gap-2`) with an input (`flex-1`) and the Add button (80px, `type="submit"`), plus the 24px reserved message line.
- Input: `placeholder="Add ticker (for example PYPL)"`, `aria-label="Ticker to add"`, same classes as the trade ticker input (`uppercase`, no `maxLength`, `autoComplete="off"`, `spellCheck={false}`).
- Unlike the trade bar, Enter DOES submit here (adding a ticker is low-stakes and reversible with the remove control).
- Submit sequence: trim; empty trimmed input shows the client error and sends nothing. Otherwise `busy` is set (Add `disabled`, input `disabled`, message "Adding {INPUT}..." with the trimmed input upper-cased), then `POST /api/watchlist`. Success: table body renders `response.watchlist` (no skeleton flash, never call the panel's `load()`), input cleared, message cleared, focus returns to the input. Failure: the server `error` text shows in the message line, the input keeps its value and re-enables.
- Re-adding an existing ticker is an idempotent 200 from the server: the list does not change, the input clears, no message. This is not an error.
- The block is rendered in every panel state but all its controls are `disabled` unless the panel state is `ready`.
- The message clears on any edit of the input, on the next submit, and after any successful add or remove.

### Watchlist remove control (inside each `WatchlistRow`)

- Fifth column, 40px, header cell contains `<span class="sr-only">Remove</span>`. The cell is `p-0 text-center`; the button is `size-8 rounded-sm text-body text-muted hover:text-down focus-visible:outline-2 focus-visible:outline-offset-2 focus-visible:outline-accent disabled:opacity-50`, content `×` with `aria-hidden="true"`, `type="button"`, `aria-label="Remove {TICKER}"`, `title="Remove {TICKER}"`. It is always visible (never hover-only, so it works on tablets and with the keyboard).
- No confirmation. Click sends `DELETE /api/watchlist/{TICKER}`. While any watchlist mutation (add or remove) is in flight, the Add button, the add input and EVERY remove button are `disabled`, so responses cannot arrive out of order. The in-flight message "Removing {TICKER}..." shows in the add block's message line.
- Success: the table renders `response.watchlist`; the row disappears. A held ticker that leaves the watchlist keeps its position row and live price in the positions table (the backend keeps it tracked). If it was the last ticker the watchlist shows its existing empty state, and the add block stays usable above it.
- Failure (for example 404 `Ticker not in watchlist`): the server text shows verbatim in the add block's message line and the row stays; no refetch.

### Positions panel (`<section data-testid="positions-panel">`)

- Title bar (40px, `px-4`, `border-b border-border`): "Positions" in Heading.
- Body: `min-h-0 flex-1 overflow-y-auto` wrapper (also `overflow-x-auto`) around `<table class="w-full min-w-144 table-fixed">`. States: loading, error, empty, populated (below).
- Columns (all headers `h-8 border-b border-border text-label text-muted font-normal`, sticky `top-0 bg-panel`):

| Column | Label | Width | Align | Content |
|--------|-------|-------|-------|---------|
| Ticker | "Ticker" | 96px | left, `px-4` | Symbol, Body 600, `truncate`, full symbol in `title` |
| Quantity | "Qty" | equal share | right, `px-2` | `fmtQty(quantity)`, `truncate` with the full value in `title` |
| Avg cost | "Avg cost" | equal share | right, `px-2` | `fmtMoney(avg_cost)` |
| Price | "Price" | equal share | right, `px-2` | `fmtMoney(livePrice)` |
| P&L | "P&L" | equal share | right, `px-2` | `fmtSigned(pnl)` colored by `toneClass`. Header `title="Unrealized P&L in dollars"` |
| P&L % | "P&L %" | equal share | right, `px-2` | `fmtPct(pnlPercent)` colored by `toneClass`. Header `title="Unrealized P&L as a percent of average cost"` |

- Rows (`h-10 border-b border-border hover:bg-raised`), keyed by ticker, in the order returned by the API (never re-sorted on the client, so rows do not jump as prices tick). Rows are not clickable in Phase 3 (ticker selection is Phase 4).
- Live values: price is `store.prices[ticker]?.price ?? position.current_price`; P&L and P&L % come from `livePosition(position, price)` (cost basis = `market_value - unrealized_pnl`, RESEARCH Pattern 6). The positions table has no flash animation (the watchlist row for the same ticker already flashes, and a second flash is noise). The label is "P&L %", not "Chg %", because it is measured against average cost, unlike the watchlist's change since session start.
- A zero P&L (after rounding) renders `0.00` and `0.00%` in `fg`.

## Interaction and Motion

- No new animation. The positions table and forms do not animate. Skeleton rows use `motion-safe:animate-pulse` (as the watchlist). The Phase 2 price flash stays on the watchlist price cell only.
- Trade lifecycle: idle, pending (buttons disabled, "Placing order..."), then success or error. Pending is entered synchronously on click, so a double-click cannot send two requests.
- Watchlist mutation lifecycle: idle, pending (add input, Add and all remove buttons disabled), then settled.
- Portfolio consistency: a trade response replaces the store's portfolio in one step, so header cash and total value, the positions table and the trade message all change in the same render. Header numbers do not flash. A `GET /api/portfolio` that started before the trade response arrived never overwrites it (ticket guard).
- Buying an unwatched ticker adds a position row (priced from `current_price` in the response) and the ticker begins streaming server-side; it does NOT appear in the watchlist panel. Selling a position to zero removes its row; the response already omits it.
- Reconnect: unchanged from Phase 2 (each transition to `connected` re-fetches the portfolio through the store's `load()`).
- Keyboard: trade bar Enter does nothing (above); watchlist add Enter submits; all new controls are reachable by Tab and show the accent focus ring.
- Focus handling: after a trade request settles focus goes to the quantity input; after an add request settles focus goes to the add input; after a remove, focus is not moved.

Server error text shown verbatim in the message line (source: `planning/API_CONTRACT.md` for the three fixed strings; the rest is the RESEARCH-recommended wording, and the planner should freeze it in `API_CONTRACT.md` because E2E will assert it):

| Situation | Server `error` text | Origin |
|-----------|---------------------|--------|
| Malformed ticker (add or trade) | `Invalid ticker: {input}` (quotes the rejected input) | Contract, fixed |
| Well-formed but never priced (add) | `Unknown ticker` | Contract, fixed |
| Remove a ticker not on the list | `Ticker not in watchlist` | Contract, fixed |
| Quantity not greater than 0 | `Quantity must be greater than 0` | Recommended (not frozen) |
| Ticker has no price (trade) | `No price available for {TICKER}` | Recommended (not frozen) |
| Not enough cash | `Insufficient cash` | Recommended (not frozen) |

| Unexpected failure | `Internal server error` | Contract, fixed |

Error-state policy (this overrides the Phase 2 "fixed strings only" rule for MUTATIONS only): trade and watchlist mutations show the server's `{"error"}` text, because the user has to know why an order was rejected. GET failures (watchlist panel, positions panel, header) still show only the fixed strings and never the body or status, as in Phase 2 (AR-04). `send()` falls back to the fixed network string when the error body is not JSON.

Open item (see Decisions Recorded 7): roadmap criterion 4 says a "malformed or unknown ticker" shows "Unknown ticker"; the frozen contract returns `Invalid ticker: X` for malformed input. This spec follows the contract.

## Decisions Recorded

1. Buy, Sell and Add are all solid `secondary` (`#753991`). Green and red stay reserved for price direction and P&L. Resolves RESEARCH assumption A4.
2. No confirmation for trades or for removing a ticker (project decision for trades; removal is reversible and keeps any held position).
3. Trade bar Enter does nothing; watchlist add Enter submits. The asymmetry is deliberate: a market order has money consequences, adding a ticker does not.
4. Messages are one reserved 24px line per form (no toast, no modal, no auto-dismiss timers). Success text is `fg`, not green.
5. Server mutation errors are shown verbatim; GET failures keep the Phase 2 fixed-string policy. This amends Phase 2's error-detail policy for mutations only.
6. Layout amendment to Phase 2: `<main>` scrolls below 1024px and panels use natural height there; at 1024px and above the Phase 2 layout holds with the workspace column now populated. The positions column label is "P&L %" (against average cost), not "Chg %" (against session start), to keep the two percentages from being confused.
7. OPEN ITEM FOR THE USER: ROADMAP criterion 4 reads "A malformed or unknown ticker is rejected with an inline 'Unknown ticker' error", but `planning/API_CONTRACT.md` (frozen in Phase 1) returns `Invalid ticker: X` for malformed input and `Unknown ticker` only for a well-formed ticker that never gets a price. This spec keeps the contract and shows the server text verbatim; both are inline rejections. In simulator mode `Unknown ticker` is unreachable (the simulator prices every well-formed symbol), so it is proved with a stub price source and a mocked-fetch component test. If the literal string is wanted for malformed input too, it is a one-line contract edit plus a one-line change in `normalize_ticker`, and no UI change.
8. The positions table has no price flash and no row click behavior (Phase 4 adds selection).
9. Positions error state needs one small store addition (`failed` flag); Header still shows `--` silently on a failed load, as in Phase 2.

Impacts on existing code the executor must handle: `Header.tsx` moves to the shared store and its tests need the store reset in `beforeEach`; `WatchlistPanel.test.tsx` and `WatchlistRow` assertions gain the fifth column; `main` and watchlist section classes change as listed under Layout.
