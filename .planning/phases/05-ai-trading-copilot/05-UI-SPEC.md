# Phase 5 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

Scope: the collapsible AI chat panel, its Header toggle, the inline action lines, and the two push channels that make a chat reply refresh the rest of the terminal (PUI-05, PUI-06). The backend (`POST /api/chat`, `GET /api/chat/history`, mock mode) is specified in `05-RESEARCH.md` and `planning/API_CONTRACT.md`; this contract only fixes what the user sees and how the panel behaves.

Sources: no CONTEXT.md (discuss-phase skipped, and this agent could not put questions to the user). Pre-populated from `05-RESEARCH.md` ("UI Design Inputs", Pitfalls 10-13, assumptions A5-A8), `planning/PLAN.md` sections 2 and 10 (docked or collapsible sidebar, loading indicator, inline confirmations, purple submit buttons), `planning/API_CONTRACT.md` (`POST /api/chat`, `GET /api/chat/history`, Action), `REQUIREMENTS.md` (PUI-05, PUI-06, CHAT-06, CHAT-08), `ROADMAP.md` Phase 5 criteria, and the existing code and specs: `02-UI-SPEC.md`, `04-UI-SPEC.md`, `globals.css`, `page.tsx`, `Header.tsx`, `TradeBar.tsx`, `FormMessage.tsx`, `ChartOverlay.tsx`, `WatchlistPanel.tsx`, `ConnectionDot.tsx`, `format.ts`, `api.ts`. This contract EXTENDS the Phase 2 and Phase 4 system (same tokens, same four type sizes, same two weights, same formatters, same panel conventions) and adds NO color tokens, NO type sizes, NO weights. Every choice that was open is marked **researcher default** and collected under "Decisions Recorded" for the user to override.

Visual focal point: the transcript is the focal point of the panel; the newest message is always in view. In the page as a whole the main chart stays the primary focal point; the chat is a secondary, collapsible region and never takes the page's focus on its own.

## Layout

Phase 2 shell and the Phase 3 and 4 grid are unchanged (`h-dvh flex flex-col`; header 48px; footer 32px; `<main>` is `lg:grid-cols-[480px_1fr]`; the watchlist is the 480px left column). Phase 5 adds one region: the chat panel. It is docked as a third column at 1536px and wider, and is a right-edge overlay drawer below that, so it never squeezes the workspace on narrower screens.

```
>= 1536px, chat open (docked)
+------------------------------------------------------------------------------------------+
| HEADER 48px     FinAlly      Total value  Cash  (dot) Live   [ Chat ]                    |
+--------------------+---------------------------------------+-----------------------------+
| WATCHLIST 480px    | WORKSPACE 1fr (696px at 1536,         | FinAlly AI          [Close] |
|                    |  1080px at 1920; Phase 4 layout       |-----------------------------|
|                    |  unchanged)                           | You 14:30                   |
|                    |                                       |        [Buy 5 AAPL        ] |
|                    |                                       | FinAlly 14:30               |
|                    |                                       | [Buying 5 AAPL now.       ] |
|                    |                                       | [Done  Bought 5 AAPL at...] |
|                    |                                       | Thinking...                 |
|                    |                                       |-----------------------------|
|                    |                                       | [textarea, 2 rows]          |
|                    |                                       | Enter sends...      [Send]  |
+--------------------+---------------------------------------+-----------------------------+
| FOOTER 32px                                                                              |
+------------------------------------------------------------------------------------------+

< 1536px, chat open (overlay drawer): the same panel, fixed to the right edge between the
header and the footer, 360px wide (full width below 640px), drawn over the workspace.
Chat closed: no panel, no column, nothing reserved.
```

- Placement: `ChatPanel` is the third child of `<main>` (after `WatchlistPanel` and the workspace `<section>`). The `<main>` class gains a conditional: when the chat is open, add `2xl:grid-cols-[480px_1fr_360px]`; when closed, the grid stays `lg:grid-cols-[480px_1fr]`. A `fixed` child takes no grid track, so below 1536px the grid is unchanged whether the drawer is open or not.
- Panel root: `<aside id="chat-panel" data-testid="chat-panel" aria-label="FinAlly AI chat" data-open="true|false">`. Open classes: `fixed top-12 right-0 bottom-8 z-20 flex w-full flex-col border-l border-border bg-panel sm:w-90 2xl:static 2xl:z-auto 2xl:h-full 2xl:min-h-0 2xl:w-auto`. Closed class: `hidden`. The panel stays mounted when closed, so the draft text, scroll position and history survive a close and reopen.
- Width budget: docked at 1536px the workspace is 1536 - 480 - 360 = 696px, so the Phase 4 mid row is two 348px columns (above the accepted 272px minimum from Phase 4) and the 576px positions table (`min-w-144`) fits without scrolling. The Phase 4 hand-off "Phase 5 owns re-flowing the mid row" is therefore satisfied by the 1536px breakpoint: no workspace change is needed. Between 1024px and 1535px the drawer covers the rightmost 360px of the workspace while open; closing it restores everything.
- Overlay presentation is non-modal: no scrim, no focus trap, the page behind stays scrollable and interactive outside the drawer. The drawer is opaque (`bg-panel`) with a 1px left border; no box shadow (shadows would add a pure-black token the theme does not have).
- Below 1024px the existing stacked layout applies (main scrolls). The drawer is 360px wide from 640px up (768px tablet: drawer over the right half) and full width below 640px. Verified widths to design against: 1920x1080, 1536x864, 1280x800, 1024x768, 768x1024. Below 640px no phone-specific work beyond the full-width drawer.
- Default state (decided in a `useEffect` after mount, never in initial state, so the static export hydrates without a mismatch): open when `window.matchMedia("(min-width: 1536px)").matches`, closed otherwise. The choice is not persisted (no localStorage); every page load decides again. At 1536px and wider the panel appears one frame after hydration (accepted).
- Header toggle: a `Chat` button at the right end of the Header's right group, after the connection dot, so it sits above the panel it controls when docked. `data-testid="chat-toggle"`, `aria-expanded="true|false"`, `aria-controls="chat-panel"`, visible text "Chat", `title="Show AI chat"` / `title="Hide AI chat"`. Style: `h-8 self-center rounded-sm border border-border px-4 text-body hover:bg-raised` plus the accent focus ring; when open the fill is `bg-raised`. It is not purple (purple is reserved for submit buttons) and not accent. The Header's right group keeps `gap-4 lg:gap-8`; at 768px the wordmark, total, cash, dot and toggle fit on one row.

### Panel anatomy (top to bottom)

| Region | Box | Content |
|--------|-----|---------|
| Title bar | `flex h-10 shrink-0 items-center justify-between border-b border-border px-4` | `<h2>` "FinAlly AI" (Heading 600); right: Close button (`data-testid="chat-close"`, text "Close", `aria-label="Close AI chat"`, `h-8 rounded-sm border border-border px-4 text-body hover:bg-raised`, accent focus ring) |
| Transcript | `data-testid="chat-messages"`, `role="log"`, `aria-live="polite"`, `aria-relevant="additions"`, `flex min-h-0 flex-1 flex-col gap-4 overflow-y-auto p-4` | History state block, or messages, loading row, local error rows |
| Composer | `<form data-testid="chat-form" aria-label="Send a message to FinAlly" aria-busy="true" while a reply is pending>`, `flex shrink-0 flex-col gap-2 border-t border-border p-4` | Textarea, then one 32px row with the hint on the left and Send on the right |

### Message presentation

Each message is a `div` (`data-testid="chat-message-user"` or `chat-message-assistant`, `data-role`) with `flex flex-col gap-1`.

- Role line (Label, muted, `flex gap-2`): "You" or "FinAlly", then the time as `HH:mm` (`fmtClock(seconds).slice(0, 5)`, `tabular-nums`, from `created_at` for stored messages and the send time for an optimistic one). User role line is right-aligned (`self-end`), assistant left-aligned. The role word, not the alignment alone, identifies the speaker.
- User bubble: `self-end max-w-72 rounded-sm border border-border bg-raised p-2 text-body text-fg whitespace-pre-wrap break-words`.
- Assistant bubble: `self-stretch rounded-sm border border-border p-2 text-body text-fg whitespace-pre-wrap break-words` (transparent, outlined). If the reply `message` is the empty string the text paragraph is omitted and only the action lines show.
- Text only. Message and ticker strings render as React text nodes: no `dangerouslySetInnerHTML`, no markdown or link rendering (XSS-safe by construction, `05-RESEARCH.md` Security Domain).
- No entrance animation on messages (dense terminal; no motion to disable). No avatars.

### Inline action lines (PUI-06)

Rendered inside the assistant bubble under the message text, only when `actions` is a non-empty list: a block `mt-2 flex flex-col gap-1 border-t border-border pt-2` holding one `data-testid="chat-action"` row per action, in the order the server returned them (trades first, then watchlist changes). Each row: `flex gap-2 text-body`, `data-ok="true|false"`, `data-kind="trade|watchlist"`.

| Part | Spec |
|------|------|
| Tag | `w-12 shrink-0 text-label font-semibold`: "Done" in `up` when `ok`, "Failed" in `down` when not |
| Sentence | `min-w-0 break-words text-fg`: built by the pure function `actionText(action)` in `frontend/src/lib/chatActions.ts` using the existing formatters. Templates in the Copywriting Contract. Failed sentences print the server `error` verbatim |

The action list is the server's record of what actually happened. The assistant's own message prose is shown as written and is never edited, hidden or reconciled with the action list. Restored history renders identical lines from the stored `actions`.

### Composer

- Textarea: `data-testid="chat-input"`, `rows={2}`, `h-16 w-full resize-none rounded-sm border border-border bg-surface p-2 text-body text-fg placeholder:text-muted` plus the accent focus ring, `aria-label="Message to FinAlly"`, `autoComplete="off"`, `spellCheck` left default. Scrolls internally beyond two lines. Not disabled while a reply is pending (the user may keep typing); disabled only while the history is loading.
- Enter sends; Shift+Enter inserts a newline. Enter does nothing while an IME composition is active (`event.nativeEvent.isComposing`), while a reply is pending, or when the trimmed draft is empty.
- Send: `data-testid="chat-send"`, `type="submit"`, text "Send", `h-8 w-20 rounded-sm bg-secondary px-4 text-body font-semibold text-fg hover:brightness-110 disabled:cursor-not-allowed disabled:opacity-50` plus the accent focus ring (identical to the Buy, Sell and Add buttons). Disabled when the trimmed draft is empty, the draft is over 2000 characters, a reply is pending, or the history is loading.
- Hint (`data-testid="chat-hint"`, Label, muted, `truncate`, `aria-live="polite"`): "Enter sends, Shift+Enter adds a line". When the draft is over 2000 characters it is replaced by "Message is too long: 2000 characters maximum" in `down`. No character counter.
- On send: the trimmed text becomes an optimistic user message at the bottom of the transcript, the textarea clears, the loading row appears below it, the transcript pins to the bottom and focus moves to the textarea (so a click on Send does not strand focus on the now-disabled button).

### Loading, slow reply and failure presentation

- Loading row (`data-testid="chat-loading"`, `aria-busy="true"`, Body, muted, `motion-safe:animate-pulse`, left-aligned like an assistant message): "Thinking..." Under `prefers-reduced-motion` the text is static. After 8 seconds without a reply the text becomes "Still thinking. This can take up to 30 seconds." (the backend timeout is 30 seconds).
- LLM failure (timeout, malformed output, missing key) is a normal 200 reply whose `message` is the assistant error text and `actions` is `[]`. It renders as an ordinary assistant message through the one rendering path; the UI never matches error strings. After a reload it is restored the same way (the backend persists the failed turn, A5).
- Request failure (network error or a 400 `{error}` from `POST /api/chat`) is local, never persisted, and renders as an error row (`data-testid="chat-error"`, `self-stretch`, Body `text-down`) directly after the optimistic user message, with the thrown `Error.message` verbatim (the server `error` text, or the fixed `NETWORK_ERROR` string already used by `api.ts`). For the network case only, a second line (Label, muted) is added: "The message may not have been processed. Check your positions before sending it again." On any request failure the sent text is put back into the textarea if the textarea is empty, so the user can edit and resend deliberately. There is no automatic or one-click resend, because a lost response may hide a trade that did execute. The optimistic user message stays in the transcript. Local error rows vanish on reload, matching the server (a failed request stored nothing).

### Behavior rules

- History: `loadHistory()` runs once on mount of `ChatPanel` (the panel is always mounted, even when closed), calls `GET /api/chat/history` and replaces `messages` with the server list (oldest first, at most 100). A successful Retry replaces the transcript with the server list, which includes any turn sent while the first load had failed; local error rows are dropped by that replacement.
- Send: a send is allowed while history is `ready` or `error`. While history is `loading` the composer is disabled. Only one reply may be pending at a time.
- Refresh on reply (testable acceptance): after a successful reply, Header total and cash, the positions table, the heatmap and the P&L chart reflect `response.portfolio` without a page reload (one `applyTrade` call; the P&L chart already refetches when the portfolio object changes), and the watchlist panel rows equal `response.watchlist`. The same two pushes happen for an LLM-failure reply, because the response always carries current state. The last write wins if a manual watchlist mutation is in flight.
- Focus: opening via the toggle moves focus to the textarea (history permitting; if the textarea is disabled, to the panel title); closing via Close or Escape returns focus to the Header toggle. Escape closes the panel only when it is presented as an overlay (viewport below 1536px) and focus is inside it; docked, Escape does nothing.
- Auto-scroll: `transcript.scrollTop = transcript.scrollHeight` in an effect keyed on message count, `sending`, history status and `open`. Always pin on new content (history is short); never `scrollIntoView` (undefined in jsdom 30). No "new messages" chip.
- Connection state: the chat uses REST, so the price-stream states (reconnecting, disconnected) neither dim nor disable it. Nothing in the panel flashes.
- No unread indicator: a reply that arrives while the panel is closed is in the transcript the next time it opens.

## Interaction and Motion

- Open and close are instant (no slide, no fade): a grid column appearing at 1536px and wider, and a `fixed` drawer below, would otherwise animate layout. No motion to disable except the pulsing loading text and skeletons, both `motion-safe:animate-pulse`.
- Focusable elements added: Chat toggle, Close, textarea, Send, example prompt buttons, chat Retry. All use the accent focus ring. Tab order inside the panel: Close, then (transcript content has no focusable items except example prompts and Retry in their states), textarea, Send. The transcript itself is not focusable (it is a live log, not a scroll widget the user must reach with the keyboard; wheel and touch scroll it).
- Keyboard: Enter, Shift+Enter and Escape as above. No global shortcut to open the panel.
- Hover: buttons use the existing `hover:bg-raised` (outline buttons) or `hover:brightness-110` (Send). Messages have no hover style.
- No confirmations and no destructive actions in this phase. Model-requested trades execute with no dialog (PLAN.md section 9, REQUIREMENTS Out of Scope).

## Decisions Recorded

Researcher defaults (no discuss-phase and no way to question the user from this agent; each is the option most consistent with PLAN.md sections 2 and 10, the prior UI-SPECs and the fixed stack; the user may override any). The first group answers the two questions the orchestrator named; the second group lists where this contract differs from the defaults in `05-RESEARCH.md` "UI Design Inputs".

Settled questions:
1. **Confirmed by the user 2026-10-09.** Dock versus overlay breakpoint: docked third column at 1536px and wider (workspace stays at least 696px, so Phase 4's mid row and positions table need no re-flow); a non-modal 360px overlay drawer below, with no scrim, no focus trap and no shadow. Default open at 1536px and wider, closed below, decided after mount and not persisted. (Confirms research A7.)
2. Failed turns after a reload: an LLM-failure turn is persisted by the backend (A5) and restored as an ordinary assistant message with no actions, the same rendering path as a live one. There is no special error styling for it, because the API carries no failure flag and the UI must not match error text. A request failure (network or 400) is a local, non-persisted `chat-error` row that disappears on reload, matching the fact that the server stored nothing.

Differences from the research defaults:
3. The Chat toggle sits at the right end of the Header (after the connection dot), not before it, so it is above the panel it opens.
4. The composer is a two-row textarea with Enter to send and Shift+Enter for a newline (research suggested a single-line input), because analysis prompts are longer than the 240px a single line would show. Hint text is always visible.
5. The textarea stays editable while a reply is pending; Send is disabled and Enter is ignored instead (research: disable the input). The draft is not lost and focus is not stripped. PUI-05 tests assert "Send disabled and Enter ignored while pending", not "input disabled".
6. The drawer is 360px wide from 640px up and full width only below 640px (research: full width below 1024px), so the tablet layout still shows the page beside the chat.
7. Example prompts in the empty state are buttons that fill the textarea and focus it; they never send (research: plain text). Filling without sending keeps "no trade without an explicit user action".
8. A slow-reply message after 8 seconds, because the backend timeout is 30 seconds.
9. Request-failure rows restore the draft and, for network failures, warn that the message may have been processed. There is no resend button: a lost response could hide an executed trade.
10. **Confirmed by the user 2026-10-09.** Messages longer than 2000 characters are blocked in the UI with an inline message. This mirrors research assumption A8, which needs a `planning/API_CONTRACT.md` edit (400 `{"error": "Message is too long"}`) before the backend enforces it; if A8 is rejected, drop only the UI limit.
11. Assistant error strings (server) are specified here so the backend and the UI copy agree. The generic one states that nothing was executed (CHAT-08).
12. No chat unread indicator, no persisted open state, no "new messages" chip, no timestamps beyond `HH:mm`, no markdown rendering, no clear-conversation control (no endpoint exists).

Impacts on existing code the executor must handle: `page.tsx` (third child, conditional grid class); `Header.tsx` (toggle); `WatchlistPanel.tsx` (watchlist push effect) and its test (an AI add or remove changes the rendered rows); `vitest.setup.ts` (`matchMedia` stub); `api.ts` and `types.ts` (chat types and calls). The chat store and watchlist store are reset in `beforeEach` like the portfolio and selection stores.
